## mygo框架

GitHub 仓库：https://github.com/egoist/mygo

### 一、简介

MyGo 是一个使用 Go 开发跨平台桌面应用的框架，同时支持原生 UI 和 Web UI。

### 二、技术特点与优缺点

| 维度     | 优点                   | 不足                     |
| -------- | ---------------------- | ------------------------ |
| 开发语言 | Go 统一业务和原生 UI   | Go UI 生态不如 Web       |
| 包体积   | 目标较低               | 实际体积取决于资源和依赖 |
| 性能     | 原生 UI 不需要 WebView | GPU UI 仍需实际测试      |
| 内存     | 原生 UI 相对轻量       | Web UI 仍有 WebView 开销 |
| 跨平台   | Windows/macOS/Linux    | 各平台系统依赖存在差异   |
| 通信     | 自动生成类型化 IPC     | 需要理解其通信机制       |
| 部署     | 安装包、签名、自动更新 | 需要配置各平台发布流程   |
| 生态     | 官方插件较丰富         | 社区生态仍需积累         |

MyGo 最有价值的地方并不是又做了一个 Go 版 Electron，而是 Go 原生 UI：不依赖 WebView，可以直接使用 Go 开发完整桌面界面

Go UI 的第三方组件生态目前不能直接与 Qt、Web 前端生态相提并论

### 三、运行平台及编译要求

根据官方文档：

| 平台            | Native UI   | Web UI            |
| --------------- | ----------- | ----------------- |
| Windows 10/11   | Direct3D 11 | WebView2          |
| macOS 12+       | Metal       | WKWebView         |
| Linux x64/ARM64 | GTK 3       | GTK 3 + WebKitGTK |

其他特点：

- 官方宣称不使用 CGO。
- 不需要安装 C/C++ 编译工具链。
- 支持交叉编译。
- Web UI 开发需要 Bun。
- 官方文档要求 Go 1.27 或更高版本。

需要注意，不使用 CGO 不代表没有平台相关依赖，也不意味着所有平台的打包和签名都可以在任意系统上完成。

### 四、项目优缺点

#### 优点

1. **Go 原生 UI：** 不依赖 WebView，可以使用 Go 开发完整桌面界面。
2. **双 UI 架构：** 原生界面和 Web 界面可以混合使用。
3. **完整桌面能力：** 窗口、托盘、快捷键、自动更新、安装包等功能都有考虑。
4. **类型化 IPC：** Go 和 TypeScript 之间的通信设计比较现代。
5. **跨平台：** 支持 Windows、macOS 和 Linux。
6. **轻量化方向：** Web UI 使用系统 WebView，避免内置 Chromium。

#### 缺点

1. Native UI 的组件丰富度、复杂表格和大型管理界面能力，需要实际验证。

2. Linux WebView 依赖 WebKitGTK，部署时需要考虑系统环境。

3. Go UI 的第三方组件生态目前不能直接与 Qt、Web 前端生态相提并论。

4. 项目生态和长期维护能力需要持续观察。

5. 跨平台功能需要分别验证，不能仅凭统一 API 就认为各平台行为完全一致。

### 五、与 Electron、Tauri、Qt 对比

| 对比          | MyGo             | Electron          | Tauri          | Qt                    |
| ------------- | ---------------- | ----------------- | -------------- | --------------------- |
| 核心语言      | Go               | JS/TS             | Rust           | C++                   |
| Web UI        | 支持             | 支持              | 支持           | 支持                  |
| 原生 UI       | 自带 GPU UI      | 不支持真正原生 UI | 依赖额外方案   | 支持                  |
| 浏览器内核    | 系统 WebView     | Chromium          | 系统 WebView   | Qt WebEngine/原生控件 |
| 是否需要 Go   | 是               | 否                | 否             | 否                    |
| 是否需要 Rust | 否               | 否                | 是             | 否                    |
| 内存开销      | 原生 UI 相对较低 | 通常较高          | 通常较低       | 视 UI 技术而定        |
| JS/Go 通信    | 类型化 IPC       | Node.js           | IPC            | WebChannel 等         |
| 适合场景      | Go 桌面应用      | Web 桌面应用      | 轻量跨平台应用 | 企业级桌面应用        |

### 六、适用场景与选型建议

| 应用场景                   | 推荐方案          |
| -------------------------- | ----------------- |
| 轻量级 Go 桌面工具         | MyGo Native UI    |
| Go 后端 + Web 前端桌面应用 | MyGo Web UI       |
| 复杂企业管理客户端         | MyGo Web UI 或 Qt |
| 大型桌面软件               | Qt                |
| Web 技术栈桌面应用         | Electron / Tauri  |
| 对内存和包体积敏感的工具   | MyGo / Tauri      |

结合企业级桌面客户端开发需求：

- **复杂企业管理客户端：** 优先考虑 Web UI + MyGo。
- **轻量工具类客户端：** 考虑 MyGo Native UI。
- **需要大量成熟桌面控件、复杂图形界面：** Qt 仍然更稳妥。

### 七、最终评价

MyGo 是一个值得关注的 Go 桌面应用框架。

它最有价值的地方并不是简单地做了一个 Go 版 Electron，而是提供了两种 UI 开发模式：

- Go 原生 GPU UI。
- 基于系统 WebView 的 Web UI。

再结合类型化 IPC、系统 API、插件、自动更新和应用打包，形成了一套相对完整的桌面应用开发方案。

但目前不应该仅凭其轻量和架构设计，就认为它已经能够全面替代 Qt。

**最终结论：如果希望使用 Go 开发跨平台桌面应用，MyGo 值得进行技术验证；如果项目涉及复杂企业级 UI、大型表格和成熟控件生态，Qt 目前仍然是更稳妥的选择。**

**个人建议使用纯go模式开发，不要使用web ui模式**
